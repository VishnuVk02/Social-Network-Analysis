========================================================================
                     PROJECT FOLDER STRUCTURE EXPLANATION
========================================================================

This file explains the purpose, use case, and rationale behind every directory
and folder in the Social Media Analytics Dashboard project.

------------------------------------------------------------------------
1. ROOT DIRECTORIES
------------------------------------------------------------------------

* backend/
  - Use Case: Houses the Node.js / Express backend API server.
  - Why to use: Separates server-side logic, database interactions, authentication,
    and external API fetches (like Reddit) from the user interface.

* frontend/
  - Use Case: Houses the Vite + React frontend web application.
  - Why to use: Keeps the client-side presentation layer isolated from the backend
    for cleaner scaling, modular deployment, and local development.

------------------------------------------------------------------------
2. BACKEND DIRECTORY STRUCTURE
------------------------------------------------------------------------

* backend/logs/
  - Use Case: Stores runtime application logs (e.g., combined.log and errors.log).
  - Why to use: Keeps persistent logs generated by the winston logging framework for
    auditing, debugging, and production monitoring.

* backend/prisma/
  - Use Case: Stores database schema definitions (schema.prisma), database seeds (seed.js),
    and historical SQL migration scripts.
  - Why to use: Prisma serves as the ORM (Object Relational Mapper). This folder manages the 
    data models (User, Group, SavedQuery, SubredditAnalytics, etc.) and tracks database
    schema changes over time.

* backend/src/
  - Use Case: Main source code folder for the Express server.
  - Why to use: Separates raw source code from configuration files, dependency lists,
    and build artifacts.

  * backend/src/config/
    - Use Case: Configuration files (e.g. db.js for PrismaClient initialization).
    - Why to use: Isolates configuration values, database connection pools, and connection
      retry/logging configurations in a single place.

  * backend/src/controllers/
    - Use Case: Intermediary handlers (e.g. auth.controller.js, group.controller.js) that
      receive HTTP requests, call appropriate service functions, and return HTTP responses.
      Acts as the "C" in MVC.
    - Why to use: Isolates routing controller logic from deep business logic and raw DB queries.

  * backend/src/middleware/
    - Use Case: Intermediate functions executed during HTTP request processing (e.g., auth,
      error handling, request logging, and 404 not-found checks).
    - Why to use: Promotes code reuse and DRY (Don't Repeat Yourself) design. Keeps routing
      controllers focused on core logic, shifting cross-cutting concerns (authentication guards,
      global error capture, request sanitization) into pipeline steps.

  * backend/src/routes/
    - Use Case: Defines REST API route mappings (endpoints like /api/auth, /api/groups) and
      maps them to their corresponding controller functions.
    - Why to use: Centralizes endpoint registration and routing paths for easy exploration.

  * backend/src/services/
    - Use Case: Contains the core business logic and database queries (e.g., user.service.js,
      reddit.service.js).
    - Why to use: Implements the "Service Layer" pattern. By separating business logic from
      controllers, services can be easily tested, reused across different endpoints, and refactored
      without affecting the HTTP request/response handling.

  * backend/src/utils/
    - Use Case: Shared utilities and helper scripts (e.g. logger.js for Winston logging).
    - Why to use: Prevents duplication of generic utilities that are imported by services,
      middlewares, and controllers.

------------------------------------------------------------------------
3. FRONTEND DIRECTORY STRUCTURE
------------------------------------------------------------------------

* frontend/src/
  - Use Case: Main source code folder for the React + Vite frontend app.
  - Why to use: Separates React components, Redux logic, and CSS files from config files.

  * frontend/src/components/
    - Use Case: Shared components that are not tied to a single feature page.
    
    * frontend/src/components/common/
      - Use Case: Reusable generic UI components (e.g. BackButton.jsx, DataTable.jsx,
        MetricCard.jsx, Navbar.jsx, Sidebar.jsx, SparkleCursor.jsx).
      - Why to use: Ensures uniform styling, centralized design updates, and rapid component
        composition.

  * frontend/src/features/
    - Use Case: Organizing by "Feature Folder Structure" rather than "Role Folder Structure".
      Contains pages, components, and Redux slices grouped together by domain area (e.g.,
      analytics, auth, dashboard, groups, reddit, settings, trends, users).
    - Why to use: Best practice for scalable React architectures. Having the components, pages,
      and Redux slice files (e.g., groupsSlice.js alongside GroupManagement.jsx) in the same
      directory makes it simple to manage and scale individual features without jumping across
      disparate directories.

  * frontend/src/services/
    - Use Case: Centralized network client configuration (e.g. api.js setting up Axios with
      interceptors to attach authorization tokens and catch expired sessions).
    - Why to use: Prevents writing custom fetch logic in every component or slice, standardizing
      error handling and base API URLs.

  * frontend/src/store/
    - Use Case: Redux Toolkit global store configuration (store.js).
    - Why to use: Integrates all the feature slices into a single global state tree.
